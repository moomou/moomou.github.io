Introduction #

I have been using Apptivate for years. It is a tiny menu-bar app that lets you bind a global hotkey to any application — press ⌥V and you are in VSCode, press ⌥C and you are in Chrome. It makes switching apps fast and easy in a way Cmd+Tab never has been.

Apptivate has not been updated in a long time and is the only Rosetta-translated app left on my Mac. So when I built WinGroup — my own Mission Control–style window grouping overlay — I figured I’d fold the per-app hotkey feature in too. How hard could it be? Activate this app when this key is pressed.

On Sonoma and Sequoia, doing that reliably across native, Electron, Chromium, Firefox, hidden, multi-instance, and cross-Space targets requires a layered cascade of private SkyLight calls, synthetic event injection, AX poking, subprocess fallbacks, and synthesized keyboard cycles. This post is about that cascade.

tl;dr macOS no longer lets a background LSUIElement app reliably bring another app’s window to the front via the public API. A working solution requires _SLPSSetFrontProcessWithOptions, a 0xf8-byte synthetic event payload ported from Hammerspoon → AltTab, AXRaise, an iTerm-style activate-with-retry loop, a /usr/bin/open -b subprocess fallback for Electron, and as a last resort a synthesized `Cmd+`` cycle.

The Naive Version #

The first version of AppShortcutService was about ten lines:

private func handleHotkey(id: UInt32) {
    let shortcut = registrations[id]!.shortcut
    let url = URL(fileURLWithPath: shortcut.path)
    let cfg = NSWorkspace.OpenConfiguration()
    cfg.activates = true
    NSWorkspace.shared.openApplication(at: url, configuration: cfg) { _, _ in }
}

This actually works for native AppKit apps when WinGroup is the foreground app. It worked great in my unit-test driver. Then I made WinGroup an LSUIElement accessory (menu-bar only, no Dock icon), which is what you want for an always-running utility, and everything fell apart.

The symptoms:

  1. Press ⌥V. Sometimes VSCode comes to front. Sometimes nothing happens.
  2. Press ⌥V again. Dock icon bounces, window does not raise.
  3. Press ⌥C for Chrome. Chrome activates but a different window than the one I last used.
  4. Press ⌥V then ⌥C quickly. ~150ms after Chrome activates, focus jumps back to VSCode unprompted.

Each one turned out to be a different layer of the macOS activation stack rejecting my request.

Why the Public API Fails #

NSRunningApplication.activate(options:) and NSWorkspace.openApplication are documented to bring an app to the front. On Sonoma+, when called from a non-foreground accessory process, they often:

  • Return true.
  • Post no notification.
  • Bounce the Dock icon.
  • Do not actually transfer keyboard focus.

This is, as far as I can tell, deliberate hardening: Apple does not want background processes hijacking the foreground app. Cooperative activation is the new model. You can request activation; the OS may grant it. The system will silently downgrade your call to a Dock bounce when it suspects you are not user-initiated, even when the call comes from a Carbon hotkey handler that very much is.

The workaround everyone reaches for (yabai, AltTab, Hammerspoon, Rectangle Pro, Raycast) is to bypass the public API and talk to WindowServer directly via the private SkyLight (CGS) framework.

Layer 1: Carbon Hotkeys, Not NSEvent #

Before any of the activation problems matter, you have to register the hotkey itself. There are two options:

  • NSEvent.addGlobalMonitorForEvents: easy, but requires Accessibility permission, does not consume the keystroke (so ⌥C will also type ç), and is unreliable across screen-lock and login-window transitions.
  • Carbon RegisterEventHotKey: older API, still fully supported, no Accessibility permission required, consumes the keystroke, survives sleep/wake.

WinGroup uses Carbon:

let id = EventHotKeyID(signature: 0x57477270, id: hkID) // 'WGrp'
RegisterEventHotKey(
    shortcut.keyCode,
    shortcut.modifiers,
    id,
    GetApplicationEventTarget(),
    0,
    &ref
)

The handler runs on the main thread, so AppKit calls from inside it are safe.

Layer 2: SLPS — The Front-Process Switch #

The private SkyLight call that actually flips the front process is:

@_silgen_name("_SLPSSetFrontProcessWithOptions") @discardableResult
func _SLPSSetFrontProcessWithOptions(
    _ psn: UnsafePointer<ProcessSerialNumber>,
    _ wid: UInt32,
    _ mode: UInt32
) -> CGError

You pass it a ProcessSerialNumber (resolved from the target pid via GetProcessForPID, itself deprecated but still functional) and the target CGWindowID. With mode = kCPSUserGenerated (0x200), it tells WindowServer “treat this as if the user clicked on this window.”

var psn = ProcessSerialNumber()
GetProcessForPID(pid, &psn)
_SLPSSetFrontProcessWithOptions(&psn, windowID, 0x200)

For native AppKit apps this is enough. For Electron and Chromium apps it is not: Chromium’s window management does not listen to the WindowServer-level front-process change directly. It watches its own run loop for AppKit notifications, which SLPS alone does not generate.

Layer 3: The 0xf8-Byte Synthetic Event #

This is where things get weird. Hammerspoon discovered around 2018 that you could wake up Chromium-based apps’ run loops by posting a specially-crafted synthetic event via another private call:

@_silgen_name("SLPSPostEventRecordTo") @discardableResult
func SLPSPostEventRecordTo(
    _ psn: UnsafePointer<ProcessSerialNumber>,
    _ bytes: UnsafePointer<UInt8>
) -> CGError

The “event” is a 248-byte (0xf8) blob whose internal layout is entirely undocumented. Hammerspoon reverse-engineered it. AltTab ported the recipe. WinGroup copies it verbatim:

private static func makeKeyWindow(psn: inout ProcessSerialNumber, windowID: CGWindowID) {
    var bytes = [UInt8](repeating: 0, count: 0xf8)
    bytes[0x04] = 0xf8        // record length
    bytes[0x3a] = 0x10        // event type
    var wid = windowID
    withUnsafeBytes(of: &wid) { src in
        for i in 0..<MemoryLayout<UInt32>.size {
            bytes[0x3c + i] = src[i]   // target window ID at offset 0x3c
        }
    }
    for i in 0x20..<(0x20 + 0x10) {
        bytes[i] = 0xff       // flags / reserved — must be 0xff
    }
    bytes[0x08] = 0x01        // phase 1
    SLPSPostEventRecordTo(&psn, &bytes)
    bytes[0x08] = 0x02        // phase 2
    SLPSPostEventRecordTo(&psn, &bytes)
}

If you omit the 0xff fill at offset 0x20, or write the windowID anywhere other than offset 0x3c, or post only one phase instead of two, the call succeeds but Chromium’s run loop never wakes up. The receiving app acknowledges the front-process switch but does not surface a window. No error, no log, just silence.

The only references for these offsets are forum posts and the source code of three open-source apps. If Apple changes the layout in a future macOS release, every cross-app window manager on the platform breaks at the same time.

Layer 4: AX, and the “Sticky Focus” Trap #

After SLPS plus the synthetic event, WindowServer thinks the right app is front. But the app may have multiple windows and we want a specific one. The Accessibility API is how you reach in and tell an app to raise a particular window:

let axApp = AXUIElementCreateApplication(pid)
let target: AXUIElement = findAXWindow(axApp: axApp, windowID: windowID, title: title)
AXUIElementPerformAction(target, kAXRaiseAction as CFString)

This works. It also has a sharp edge.

The natural extension is to also set kAXMainAttribute = true, kAXFocusedAttribute = true, and on the app kAXFocusedWindowAttribute = target. The AX docs read like that’s what they’re for. Don’t do it.

If you set these attributes, the app remembers the chosen window as its main/focused window. When the user later presses Cmd+N to open a new document, the new window does not become focused. Focus stays stuck on the window you marked. New windows appear unfocused, behind the old one, and typing goes nowhere.

I called this the “sticky focus” bug. Tracking it down took an entire weekend. The fix is to do AXRaise and only AXRaise. No kAXMain, no kAXFocused, no kAXFocusedWindow. Apptivate sidesteps the trap by doing tell app "VSCode" to activate via AppleScript: it never picks a specific window, so there’s nothing to stick. But picking a specific window is the whole point of per-Space last-window memory, so that escape hatch is closed for us.

// NOTE on what we are deliberately NOT doing:
//   • kAXMainAttribute=true on the window         ← sticks; new windows don't promote
//   • kAXFocusedAttribute=true on the window      ← sticks; same problem
//   • kAXFocusedWindowAttribute=target on app     ← sticks; same problem
//   • kAXFrontmostAttribute=true on the app       ← redundant with SLPS, can race

Layer 5: HID-Active Lag (the iTerm Retry) #

SLPS updates WindowServer. The synthetic event wakes the target’s run loop. AXRaise picks the window. We are done, right?

No. There is another layer below WindowServer: the HID input layer, which decides where keyboard events are routed. On Sonoma+, when called from an accessory process, the HID layer often does not follow the WindowServer change for ~150ms. Sometimes longer. Sometimes never.

The symptom: the visual front app changes but keystrokes still go to whatever was previously focused. You see VSCode in front, you start typing, and your text appears in the Slack channel you had open before.

iTerm2 hit this exact problem and documented their workaround in iTermApplication.m: call NSRunningApplication.activate(...) repeatedly until NSWorkspaceDidActivateApplicationNotification fires for the target pid. WinGroup copies this:

let delays: [Double] = [0.0, 0.05, 0.15, 0.30, 0.60, 1.0]
for delay in delays {
    DispatchQueue.main.asyncAfter(deadline: .now() + delay) { [weak runningApp] in
        guard stillPending, let app = runningApp else { return }
        if app.isActive { return }
        app.activate(options: [.activateIgnoringOtherApps])
    }
}

The retry loop is observed by an NSWorkspace notification observer that cancels remaining attempts as soon as activation lands. Without it you get duplicate Dock bounces and the focus can flicker.

There’s a critical detail here: the retry loop has to be cancelled across pids, not just within a pid. I learned this the hard way.

If the user presses ⌥C (Chrome) and 100ms later presses ⌥V (VSCode), the Chrome retry loop is still firing app.activate(...) in the background. About 150ms after VSCode activates, one of those Chrome retries lands and steals focus back. The visible behavior is “I pressed VSCode but I’m in Chrome.” The fix: only one in-flight activation at a time, ever.

pendingLock.lock()
for (_, prev) in pendingActivations {
    nc.removeObserver(prev)
}
pendingActivations.removeAll()
pendingLock.unlock()

Layer 6: The /usr/bin/open Subprocess Fallback #

Even with the iTerm retry, some apps (most notably Electron-based VSCode) silently reject in-process NSRunningApplication.activate(...) from an accessory caller. The call returns success, no notification fires, the app does not come forward, and repeating it does not help.

The /usr/bin/open binary, run as a separate user-owned subprocess, gets full activation rights from Launch Services where our in-process call does not. Empirically:

$ open -b com.microsoft.VSCode    # works
osascript -e 'tell app "Visual Studio Code" to activate'    # silently rejected
NSRunningApplication.activate(...)    # silently rejected

So at the 250ms mark, if HID-active still has not landed, WinGroup spawns:

let task = Process()
task.launchPath = "/usr/bin/open"
task.arguments = ["-b", bundleID]
try task.run()

open -b is a no-op when the app is already running with windows; it just activates. Safe to fire even when not strictly needed.

Layer 7: The Cmd+` Last Resort #

For one specific class of stuck-focus scenarios, usually involving VSCode on a different Space we just switched away from, even open -b does not promote a window to key status inside the app. The app receives HID input but has no internal “key window” assigned, so typing goes nowhere.

The empirical workaround was: “after the hotkey, I press Cmd+ and it works." Cmd+ is the standard “cycle windows within app” shortcut. Pressing it forward then backward nets to the same window, but forces the app’s internal window-cycling code path to assign key status to whatever it lands on.

So at the 700ms mark, if nothing else has worked, WinGroup synthesizes the cycle and posts it directly to the target pid:

private static func postBackquoteCycle(pid: pid_t) {
    let src = CGEventSource(stateID: .hidSystemState)
    let key: CGKeyCode = 0x32   // kVK_ANSI_Grave

    let d1 = CGEvent(keyboardEventSource: src, virtualKey: key, keyDown: true)
    d1?.flags = .maskCommand
    d1?.postToPid(pid)
    // ... up, then down with shift, then up with shift
}

postToPid (not .cghidEventTap) means the event is delivered only to the target process: no risk of leaking `Cmd+`` to whatever the OS thinks is frontmost if SLPS still hasn’t won.

It’s the ugliest piece of code in the project. It also reliably unsticks VSCode where nothing else does, so it stays.

Layer 8: Per-Space Last-Window Memory #

All of the above just gets a window of the target app to front. The Apptivate-style behavior I want is more specific: for each desktop Space, remember the last window of this app the user raised on that Space.

So if on Space 1 you were in VSCode workspace mono and on Space 2 you were in VSCode workspace notes, pressing ⌥V on each Space should return you to the workspace that belongs there.

private struct SpaceKey: Hashable {
    let bundleKey: String
    let spaceID: UInt64
}
private var lastWindowID: [SpaceKey: UInt32] = [:]

The active Space ID comes from a private CGS query against copyManagedDisplaySpaces (with a fallback to CGSGetActiveSpace). When the hotkey fires, we filter CGWindowList to .optionOnScreenOnly, which only returns windows on the current Space, and prefer the remembered windowID if it is still on-screen. Otherwise we pick the topmost on-Space window — same semantics as the system Cmd+` cycle.

Layer 9: The Edge Cases #

A non-exhaustive list of things that broke in real-world use:

  • Hidden apps drop out of CGWindowList even when their windows are on the current Space. We unhide() every running instance up front.
  • Some apps (Slack notably) register more than one Launch Services process per bundle ID. The window owner PID we see in CGWindowList may not match runningApplications.first, so we collect all pids for the bundle ID before filtering windows.
  • AX takes time to populate the destination Space’s window list after a Space switch. We poll AX every 80ms for up to 8 attempts after activation and re-AXRaise once the target window appears.
  • Apps with no on-screen windows on the current Space: we can’t pick a specific window, but we still want the app’s keyboard shortcuts to work, so we run the activation cascade with windowID = 0 as a sentinel that skips the post-activation re-raise.
  • Folder paths instead of .app paths. Apptivate let you bind hotkeys to folders too. We pass those to NSWorkspace.open and short-circuit the rest.
  • kCGWindowName requires Screen Recording permission on Sonoma+. We use windowID as the primary match key and treat title as diagnostic-only; the Screen Recording prompt is ugly and not worth requiring.

Architecture, Such As It Is #

The full activation cascade for a single hotkey press, in order:

  1. Carbon RegisterEventHotKey handler fires on the main thread.
  2. Resolve target via AppShortcutService.activateApp — bundleID → all running instances → unhide hidden ones → enumerate on-screen windows on the current Space → pick the per-Space-remembered window or fall back to topmost.
  3. WindowActivator.raise runs the cascade:
    • Resolve the AXUIElement up front (cached, survives Space switches).
    • _SLPSSetFrontProcessWithOptions(psn, windowID, 0x200).
    • Two SLPSPostEventRecordTo synthetic events (the 0xf8-byte payload).
    • AXUIElementPerformAction(target, kAXRaiseAction) — and nothing else AX-wise.
  4. scheduleHIDActivation launches the retry stack:
    • Cancel any in-flight activation for any other pid.
    • Register NSWorkspace activation observer.
    • Schedule app.activate(...) retries at 0/50/150/300/600/1000ms.
    • Schedule /usr/bin/open -b <bundleID> subprocess at 250ms.
    • Schedule `Cmd+`` cycle at 700ms.
    • Final timeout / observer cleanup at 1500ms.
  5. scheduleAXRetry polls AX every 80ms for up to 640ms in case the AX window list lagged the front-process switch, and re-runs AXRaise once it lands.

That’s the working solution for “press a key, focus an app.” On a clean modern AppKit app with one window on the current Space, only steps 1–3 actually do anything observable. The rest exists because of Electron, hidden apps, multi-Space targets, and accessory-process activation rules. Which between them describe most of the apps anyone uses every day.

Reflection #

What I thought was a weekend project turned into a multi-week tour through the source of yabai, AltTab, Hammerspoon, and iTerm2. There is no public API that does what every window utility on macOS needs, so we all converge on the same private cascade.

A few things stuck with me:

  • Read comparable open-source apps before writing code. The 0xf8 byte layout, the iTerm retry pattern, the “do not set kAXMain” rule — none of these are documented anywhere except as comments inside other people’s source.
  • Log with timestamps. Activation bugs are timing bugs. Without per-step logs I would never have caught the cross-pid retry stealing focus, or that Cmd+` was what unstuck VSCode.
  • The trap doors are the AX attributes that look like they should help. kAXMain, kAXFocused, kAXFocusedWindow each look documented and useful, and each creates a long-lived bug when set from outside the app. Only AXRaise.

This is also the kind of project that’s dramatically more tractable in 2026. Reverse-engineering an undocumented byte layout used to be a weeks-long grep across other people’s repos. With AI assistance the discovery loop is much tighter: paste a Hammerspoon comment, get a hypothesis, verify in AltTab, write the Swift.

The end result is that ⌥V takes me to my last VSCode window on the current Space in under 200ms, every time, regardless of whether VSCode was hidden, on a different Space, or had no windows at all. Eight layers of fallback for a single keystroke is a lot, but having ⌥V just work again after months of Apptivate getting flakier turned out to be worth all of it.
